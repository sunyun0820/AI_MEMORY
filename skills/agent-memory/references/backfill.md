# Backfill Reference

Backfill은 **완료되었거나 충분히 진행된 현재 세션을 사후 회고하여, 실시간 Remember에서 놓친 재사용 지식을 복구하는 모드**입니다.

권장 호출:

```text
agent_memory backfill
```

## 목적

Backfill은 세션 전체를 요약하거나 구현 내역을 보존하는 작업이 아닙니다.

```text
현재 세션/작업 기록
→ 시행착오/숨은 제약/설계 이유/검증 지식 추출
→ 재발 방지 관점으로 압축
→ 공용화 가능성 판단
→ 필요한 것만 AI_MEMORY에 저장
```

핵심 질문은 `무엇을 구현했는가`보다 다음입니다.

- 다음 Agent가 무엇을 잘못하면 안 되는가?
- 무엇을 먼저 확인하면 시행착오를 줄일 수 있는가?
- 어떤 구조/경계/관례가 미래 판단에 중요할까?
- 어떤 패턴을 다른 작업에도 재사용할 수 있는가?

## Source 사용 원칙

Backfill의 입력은 **현재 세션/history**입니다. Backfill을 위해 별도 프로젝트 Source를 다시 확보하거나 감사하지 않습니다.

- 현재 세션에서 이미 확인된 코드, 설정, 테스트, 로그, 문서, 사용자/팀 지시는 근거로 사용할 수 있습니다.
- 과거 Source가 현재 PC에 없더라도 세션에서 확정된 지식의 가치가 사라지지 않습니다.
- `Source가 없음`을 이유로 저장 후보를 폐기하거나 confidence를 낮추지 않습니다.
- `소스 미확보`, `현재 소스 확인 필요` 같은 문구를 Memory에 추가하지 않습니다.
- 후보의 사실성이 세션 자체에서 불확실하면 확정 사실로 저장하지 않거나 불확실성을 그대로 남깁니다. 이를 해결하려고 Source Audit을 시작하지 않습니다.

즉 **세션에서 이미 얻은 지식은 추출하고, 세션 밖의 Source를 새로 조사하지 않습니다.**

## 후보 우선순위 휴리스틱

아래 점수는 절대 규칙이 아니라 내부 정렬용입니다.

```text
+5  재발 방지 가치가 높은 실수/오판/잘못된 가정
+5  다른 모듈/프로젝트에도 적용 가능한 공용 Lesson
+5  숨은 불변조건/위험한 경계/깨지면 안 되는 동작
+4  확인하기 어려웠던 Root Cause + 해결 메커니즘
+4  설계 선택 이유 / 폐기안과 폐기 이유
+3  검증된 디버깅/빌드/배포/DB/마이그레이션 절차
+3  미래 탐색 비용을 크게 줄이는 Source Navigation 또는 버전 구조 지식

-5  단순 구현 완료 요약
-5  변경 파일/클래스 목록
-4  현재 세션 진행 상태/TODO
-4  미래 판단 가치가 없는 단순 변경 사실
-3  일반 문서나 기초 지식으로 쉽게 얻는 내용
```

## 공용화 판단

각 후보를 저장하기 전에 확인합니다.

```text
이 지식은 현재 프로젝트/버전에만 유효한가?
같은 메커니즘을 가진 다른 작업에도 적용 가능한가?
일반화한다면 적용 조건은 무엇인가?
적용하면 안 되는 예외는 무엇인가?
```

특정 Incident에서 공용 Lesson이 도출되면 서로 다른 미래 가치가 있을 때만 분리합니다.

```text
Project / Incident
- 실제 장애 맥락
- 구체적인 Root Cause
- 프로젝트/버전 특수 제약

General Lesson
- 다른 작업에도 재사용 가능한 핵심 패턴
- 적용 조건
- 재발 방지 체크
```

프로젝트 이름만 제거한 복사본은 만들지 않습니다.

## 1. 실수 / 시행착오 / 재작업

가능하면 다음 구조로 정리합니다.

```text
증상
→ 잘못된 접근 또는 잘못된 가정
→ 확인된 원인
→ 올바른 해결
→ 재발 방지 규칙
→ 다른 곳에도 적용 가능한지
```

저장 가치가 높은 예:

- 존재하지 않는 클래스/파일/옵션을 있다고 가정해 잘못 수정함
- 영향 범위를 확인하지 않고 과도하게 변경해 재작업함
- 같은 종류의 실패가 반복됨
- 오류 메시지만 보고 원인을 잘못 단정했지만 이후 실제 원인이 확인됨
- 프로젝트에서 나온 실수가 다른 CUD/트랜잭션/빌드/배포 작업에도 반복될 수 있음

중간의 틀린 결론 자체는 사실처럼 저장하지 않습니다. 틀린 접근이 재발 방지에 가치가 있을 때만 Wrong Approach로 남깁니다.

## 2. 프로젝트 로직 / 불변조건 / 버전 지식

다음 Agent가 모르고 건드리기 쉬운 것을 우선합니다.

- 기존 프로그램이 의도적으로 현재 방식으로 동작하는 이유
- 특정 수정 시 깨질 수 있는 연관 기능
- 데이터 정합성 규칙
- 호출 순서나 생명주기 제약
- 모듈/서비스 간 중요한 의존관계
- 환경/버전별 차이
- 변경 금지 또는 반드시 검증해야 하는 경계
- 미래 탐색 비용을 크게 줄이는 Source Navigation Map

현재 세션에서 해당 지식이 코드/설정/테스트로 이미 확인되었다면 그 사실을 근거로 적을 수 있습니다. **Backfill을 위해 다시 Source를 열어 확인하지 않습니다.**

프로젝트 구조가 특정 버전에서 확인된 것이라면 `3.5.2에서 확인된 구조`처럼 시점/버전 경계를 남깁니다.

## 3. 설계 결정과 폐기안

단순히 `A를 선택함`만 저장하지 않습니다.

```text
문제/조건
→ 검토한 선택지
→ 최종 선택
→ 선택 이유
→ 버린 방식과 버린 이유
→ 이후 재검토 조건
```

미래 작업에 영향을 주지 않는 일회성 선택은 저장하지 않습니다.

## 4. 검증 / 디버깅 / 운영 절차

재사용 가능한 순서가 확인된 경우 저장 후보입니다.

- 어떤 로그/파일/DB/명령을 어떤 순서로 확인해야 하는지
- 겉으로 정상처럼 보여도 추가 확인해야 하는 포인트
- PASS/FAIL 판정 기준
- 안전한 빌드/배포/마이그레이션 순서
- 과거에 놓쳤던 확인 단계

일반적인 공식 문서 수준의 절차보다 실제 시행착오에서 얻은 순서를 우선합니다.

## 5. 구현 요약 억제

다음 형태로 Backfill 결과가 쏠리지 않도록 합니다.

```text
API 구현
Entity 추가
Repository 수정
설정값 추가
빌드 성공
```

대신 다음 질문으로 변환합니다.

```text
왜 이 구조여야 하는가?
어떤 제약 때문에 다른 방식은 위험한가?
미래에 어디서부터 확인하면 되는가?
비슷한 구현에서 어떤 실수를 피해야 하는가?
```

변환해도 의미 있는 지식이 나오지 않으면 저장하지 않습니다.

이 판단은 **Source를 다시 열어봐야 한다는 뜻이 아닙니다.** 세션에서 얻은 정보만으로 장기 가치가 있는지 판단합니다.

## 6. 반복 작업 / Tool 후보

다음 특성이 반복되면 Tool 후보로 봅니다.

- 여러 파일에서 동일 패턴 탐색
- 고정 규칙 기반 비교/집계/검증
- 같은 명령/검색/파일 변환 반복
- AI 판단보다 결정적 처리 비중이 큼
- AI가 직접 읽으면 토큰을 많이 쓰지만 스크립트로 요약 가능

구분:

- `new-tool`: 아직 대응 Tool이 없고 새 Tool로 분리할 가치가 있음
- `improvement`: 기존 Tool/Script의 버그, 기능 부족, 경로/출력 문제, 안정성/사용성 개선

Tool 후보가 있으면 `TOOL_CANDIDATES.md`에 목적/대상/입출력/문제 형태 기준으로 중복 병합합니다. 후보는 backlog에만 기록하고 Backfill 중 구현하지 않습니다. 후보 전용 항목을 `TOOL_INDEX.md`에 넣지 않습니다.

## 7. 미해결 위험 / 기술 부채

다음 세션에서도 반드시 알아야 하는 지속적 위험만 저장 후보입니다.

- 임시 우회로 남은 문제
- 다음 작업에서 확인해야 하는 경계
- 오래 유지될 가능성이 높은 기술 부채

금방 사라지는 TODO나 단순 진행 상태는 저장하지 않습니다.

## 저장 필터

1. **재사용성**: 미래 작업에서 다시 도움이 되는가?
2. **공용화 가능성**: 더 넓게 쓸 수 있는 패턴을 추출할 수 있는가?
3. **재발 방지 가치**: 다음 Agent의 실수/오판을 실제로 줄이는가?
4. **비자명성**: 단순 구현 기록 이상의 판단 가치가 있는가?
5. **적용 경계**: 언제 적용되고 언제 적용하면 안 되는지 설명 가능한가?
6. **근거성**: 현재 세션에 이미 있는 경험/코드/설정/테스트/로그/문서/사용자 확인 등 근거가 있는가?
7. **지속성**: 세션 종료 후에도 의미가 남는가?
8. **중복성**: 기존 AI_MEMORY에 동일하거나 더 좋은 기억이 없는가?

6번은 **새 Source 확보 의무가 아닙니다.**

## 기존 기억과 충돌할 때

- 현재 세션에서 이미 명확히 확인된 사실이나 사용자 수정이 기존 Memory와 충돌하면 새 근거를 반영합니다.
- 기존 Memory를 무조건 덮어쓰지 않습니다.
- 어느 쪽이 맞는지 현재 세션 정보만으로 구분되지 않으면 확정 규칙으로 저장하지 않습니다.
- 충돌 해결만을 위해 별도 프로젝트 Source를 찾지 않습니다.

## 세션 범위 한계

Host Agent가 오래된 대화 일부를 더 이상 볼 수 없거나 컨텍스트가 압축/잘린 경우:

- 보이는 범위만 검토합니다.
- 누락된 과거를 추측하지 않습니다.
- 현재 세션 밖의 Source로 빠진 대화 맥락을 대신 복원하려 하지 않습니다.

```text

- 버린 저가치 구현요약: N
- 세션 범위 제한: 없음 / 있음
```
