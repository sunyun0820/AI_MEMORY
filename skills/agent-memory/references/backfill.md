# Backfill Reference

Backfill은 **완료되었거나 충분히 진행된 현재 세션을 사후 회고하여, 실시간 Learn/Remember에서 놓친 재사용 지식을 복구하는 모드**입니다.

권장 호출:

```text
agent_memory backfill
```

## 목적

세션 전체를 요약하거나 구현 내역을 보존하는 것이 목적이 아닙니다.

Backfill의 핵심 목적은:

```text
과거 작업
→ 시행착오/숨은 제약/설계 이유/검증 지식 추출
→ 다른 작업에도 재사용 가능한지 일반화
→ 재발 방지 관점으로 압축
→ 필요한 것만 AI_MEMORY에 저장
```

입니다.

단순히 `무엇을 구현했는가`보다 **다음 Agent가 무엇을 잘못하면 안 되는가, 무엇을 먼저 확인해야 하는가, 어떤 패턴을 다른 곳에도 재사용할 수 있는가**를 우선합니다.

## 후보 우선순위 휴리스틱

아래 점수는 기계적인 절대 기준이 아니라 후보를 정렬하기 위한 내부 휴리스틱입니다.

```text
+5  재발 방지 가치가 높은 실수/오판/잘못된 가정
+5  다른 모듈/프로젝트에도 적용 가능한 공용 Lesson
+5  숨은 불변조건/위험한 경계/깨지면 안 되는 동작
+4  확인하기 어려웠던 Root Cause + 검증된 해결
+4  설계 선택 이유 / 폐기안과 폐기 이유
+3  검증된 디버깅/빌드/배포/DB/마이그레이션 절차
+3  미래 탐색 비용을 크게 줄이는 Source Navigation 지식

-5  단순 구현 완료 요약
-5  변경 파일/클래스 목록
-4  현재 세션 진행 상태/TODO
-4  Git diff나 현재 소스로 쉽게 복원 가능한 사실
-3  일반 문서나 기초 지식으로 쉽게 얻는 내용
```

총점이 낮거나 미래 판단에 직접 도움이 되지 않는 후보는 저장하지 않는 쪽을 우선합니다.

## 공용화 판단

각 후보를 저장하기 전에 반드시 아래를 확인합니다.

```text
이 지식은 현재 프로젝트에만 유효한가?
같은 메커니즘을 가진 다른 작업에도 적용 가능한가?
일반화한다면 적용 조건은 무엇인가?
적용하면 안 되는 예외는 무엇인가?
```

특정 Incident에서 공용 Lesson이 도출되면 둘을 분리할 수 있습니다.

예:

```text
Incident / Project Memory
- 실제 장애 맥락
- 구체적인 파일/메서드/Root Cause
- 프로젝트 특수 제약

General Lesson
- 다른 작업에도 재사용 가능한 핵심 패턴
- 적용 조건
- 재발 방지 체크
```

단, 두 파일이 같은 내용을 반복할 뿐이면 하나만 남깁니다.

## 1. 실수 / 시행착오 / 재작업

가능하면 다음 구조로 정리합니다.

```text
증상
→ 잘못된 접근 또는 잘못된 가정
→ 확인된 원인
→ 올바른 해결
→ 다음에 지켜야 할 재발 방지 규칙
→ 다른 곳에도 적용 가능한지
```

저장 가치가 높은 예:

- Agent가 존재하지 않는 클래스/파일/옵션을 있다고 가정해 잘못 수정함
- 영향 범위를 확인하지 않고 과도하게 변경해 재작업함
- 같은 종류의 실패가 세션 안에서 반복됨
- 오류 메시지만 보고 원인을 잘못 단정했지만 이후 실제 원인이 확인됨
- 특정 프로젝트에서 나온 실수가 다른 CUD/트랜잭션/빌드/배포 작업에도 반복될 수 있음

중간의 틀린 결론 자체를 사실처럼 저장하지 않습니다. 틀린 접근이 재발 방지에 가치가 있을 때만 `wrong approach`로 남깁니다.

## 2. 프로젝트 로직 / 불변조건 / 제약

다음 Agent가 모르고 건드리기 쉬운 것을 우선합니다.

- 기존 프로그램이 의도적으로 현재 방식으로 동작하는 이유
- 특정 수정 시 깨질 수 있는 연관 기능
- 데이터 정합성 규칙
- 호출 순서나 생명주기 제약
- 모듈/파일/서비스 간 중요한 의존관계
- 환경별 차이
- 변경 금지 또는 반드시 검증해야 하는 경계

현재 코드/설정/테스트로 검증할 수 있으면 검증 후 저장합니다.

단순 클래스/메서드 목록은 저장하지 않습니다. 다만 미래 탐색 비용을 크게 줄이고 잘못된 진입점을 막는 Source Navigation Map은 예외적으로 가치가 있습니다.

## 3. 설계 결정과 폐기안

단순히 `A를 선택함`만 저장하지 않습니다.

가능하면 다음을 남깁니다.

```text
문제/조건
→ 검토한 선택지
→ 최종 선택
→ 선택 이유
→ 버린 방식과 버린 이유
→ 이후 재검토가 필요한 조건
```

미래 작업에 영향을 주지 않는 일회성 선택은 저장하지 않습니다.

## 4. 검증 / 디버깅 / 운영 절차

재사용 가능한 순서가 확인된 경우 저장 후보입니다.

예:

- 어떤 로그/파일/DB/명령을 어떤 순서로 확인해야 하는지
- 겉으로 정상처럼 보여도 추가 확인해야 하는 검증 포인트
- PASS/FAIL 판정 기준
- 안전한 빌드/배포/마이그레이션 순서
- 과거에 놓쳤던 확인 단계가 무엇이었는지

일반적인 공식 문서 수준의 절차는 저장하지 않고, 프로젝트 특이사항이나 실제 시행착오에서 얻은 순서를 우선합니다.

## 5. 구현 요약 억제

다음 형태로 Backfill 결과가 쏠리지 않도록 합니다.

```text
- API 구현
- Entity 추가
- Repository 수정
- 설정값 추가
- 빌드 성공
```

이런 내용은 대개 Git/소스에서 복원할 수 있으므로 장기 Memory 가치가 낮습니다.

대신 아래처럼 변환 가능한 경우에만 저장합니다.

```text
구현 사실
→ 왜 이 구조여야 하는가?
→ 어떤 제약 때문에 다른 방식은 위험한가?
→ 미래에 어디서부터 확인하면 되는가?
→ 비슷한 구현에서 어떤 실수를 피해야 하는가?
```

변환해도 의미 있는 지식이 나오지 않으면 저장하지 않습니다.

## 6. 반복 작업 / Tool 후보

Backfill 중 아래 특성이 반복적으로 보이면 Tool 후보로 봅니다.

- 여러 파일에서 동일 패턴 탐색
- 고정 규칙 기반 비교/집계/검증
- 같은 명령/검색/파일 변환을 반복
- AI 판단보다 결정적 처리 비중이 큼
- AI가 직접 읽으면 토큰을 많이 쓰지만 스크립트로 요약 가능

Tool 관련 발견은 반드시 둘로 구분합니다.

- `new-tool`: 아직 대응 Tool이 없고, 반복/대량/결정적 작업을 새 Tool로 분리할 가치가 있는 경우
- `improvement`: 이미 존재하는 Tool/Script의 버그, 경로/출력 문제, 기능 부족, 안정성 또는 사용성 개선이 필요한 경우

기존 Tool/Script의 문제를 새 Tool 후보로 잘못 분류하지 않습니다.

### Tool 후보 공용 Backlog

Tool 후보나 개선사항이 하나라도 발견되면 `AI_MEMORY/TOOL_CANDIDATES.md`를 읽고 **자동 누적/중복 병합**합니다.

절차:

1. `TOOL_CANDIDATES.md`를 읽습니다.
2. 후보 이름이 아니라 **목적 + 대상 + 입력/출력 + 문제 형태**를 기준으로 동일/유사 후보를 찾습니다.
3. `dedup_key`가 있으면 우선 비교하고, 키가 달라도 사실상 같은 문제면 중복으로 취급합니다.
4. 동일 후보가 있으면 새 항목을 만들지 않고:
   - `occurrences` 증가
   - `last_seen` 갱신
   - 새 프로젝트가 있으면 `projects` 병합
   - 새로운 근거만 `evidence`에 추가
   - 검증 수준이 실제로 높아졌을 때만 `verification` 강화
5. 동일 후보가 없으면 `templates/TOOL_CANDIDATE_TEMPLATE.md` 형식으로 새 항목을 추가합니다.
6. 후보가 없으면 `TOOL_CANDIDATES.md`를 수정하지 않습니다.
7. 후보는 backlog에만 기록하며 Backfill 중 실제 Tool/Script를 구현하거나 고치지 않습니다.
8. 후보를 `TOOL_INDEX.md`에 등록하지 않습니다. `TOOL_INDEX.md`는 구현 및 검증이 끝난 실제 Tool 전용입니다.

Tool 후보마다 가능하면 다음을 유지합니다.

```text
kind
대상
occurrences
first_seen / last_seen
관련 프로젝트
검증 수준
입력 / 출력 (new-tool일 때)
토큰 / 시간 / 오류 절감 기대효과
구현 난이도
추천도
근거
```

## 7. 미해결 위험 / 기술 부채

다음 세션에서도 반드시 알아야 하는 지속적 위험만 저장 후보입니다.

- 임시 우회로 남은 문제
- 아직 검증되지 않아 다음 작업에서 반드시 확인해야 하는 경계
- 오래 유지될 가능성이 높은 기술 부채

금방 사라지는 TODO나 단순 진행 상태는 저장하지 않습니다.

## 저장 필터

아래 순서로 Memory 후보를 줄입니다.

1. **재사용성**: 미래 작업에서 다시 도움이 될 가능성이 있는가?
2. **공용화 가능성**: 현재 사례에서 더 넓게 쓸 수 있는 패턴을 추출할 수 있는가?
3. **재발 방지 가치**: 다음 Agent의 실수/오판을 실제로 줄이는가?
4. **비자명성**: 일반 검색/기초 지식/현재 소스로 바로 얻을 수 없는가?
5. **적용 경계**: 언제 적용되고 언제 적용하면 안 되는지 설명 가능한가?
6. **검증성**: 실제 코드, 설정, 테스트, 로그, 사용자 확인 등으로 근거가 있는가?
7. **지속성**: 현재 세션이 끝난 뒤에도 의미가 남는가?
8. **중복성**: 기존 AI_MEMORY에 동일하거나 더 좋은 기억이 없는가?

여러 항목에서 명확히 실패하면 Memory에는 저장하지 않는 쪽을 우선합니다.

Tool 후보 backlog는 Memory와 별도입니다. 아직 검증 전인 자동화 아이디어도 `verification: needs-validation` 상태로 후보에는 남길 수 있지만, 근거 없는 아이디어를 억지로 생성하지 않습니다.

## 기존 기억과 충돌할 때

- 최신 코드/설정/테스트/명시적 사용자 지시를 우선합니다.
- 기존 기억을 무조건 덮어쓰지 않습니다.
- 기존 기억이 틀렸다고 검증되면 수정하고 변경 이유를 남깁니다.
- 어느 쪽이 맞는지 검증되지 않으면 확정 규칙으로 저장하지 않습니다.

## 세션 범위 한계

Host Agent가 오래된 대화 일부를 더 이상 볼 수 없거나 컨텍스트가 압축/잘린 경우:

- 보이는 범위만 분석합니다.
- 보지 못한 과거 내용을 추측해 채우지 않습니다.
- 최종 보고에 `세션 전체가 아니라 현재 접근 가능한 범위만 Backfill함`이라고 명시합니다.

## 최종 보고 형식

길게 회고 보고서를 만들 필요는 없습니다. 기본적으로 아래만 짧게 보고합니다.

```text
Backfill 결과
- 신규 저장: N
- 기존 기억 업데이트/중복 병합: N
- 공용화한 Lesson: N
- 핵심 재발 방지 규칙: ...
- 핵심 프로젝트 제약: ...
- Tool 신규 후보: N개 / backlog 신규·병합 결과
- Tool/Script 개선사항: N개 / backlog 신규·병합 결과
- 구현요약이라 저장 제외: ...
- 기타 저장 제외: ...
- 세션 범위 제한: 없음 / 있음
```

Memory에 저장할 가치가 있는 내용이 없어도 Tool 후보/개선사항이 있으면 backlog만 갱신할 수 있습니다.

Memory와 Tool 후보가 모두 없다면 억지로 만들지 말고 다음처럼 종료합니다.

```text
저장할 가치 있는 신규 기억 없음
Tool 후보/개선사항 없음
```
