# DB 접근 및 자격 증명 규칙

- 어떤 DB 환경(dev/test/stage/prod 포함)에도 사용자의 명시적 승인 없이 접속하거나 작업하지 말라.
- DB 접근 전 목적, 대상 환경/DB, 읽기·쓰기 여부, 수행 범위를 보고하고 승인을 받아라.
- 승인된 범위를 넘어서는 조회, 변경, DDL/DML, 마이그레이션, 백업·복구, 권한 변경은 별도 승인을 받아라.
- DB 접속정보, 비밀번호, 토큰, 인증서, SSH 정보 등 비밀값을 장기 메모리, 코드, 설정, 로그, 대화 요약, Git 등에 저장하지 말라.
- 사용자가 제공한 비밀값은 현재 작업에만 일시적으로 사용하고 응답에 원문으로 재출력하지 말라.
- 가능한 경우 최소 권한, 읽기 전용, 테스트 환경, dry-run 및 롤백 가능한 방법을 우선 사용하라.

# Git 안전 규칙

- 사용자의 명시적 요청 없이 commit, push, branch/tag 생성·삭제, merge, rebase, reset, revert, cherry-pick 등 저장소 상태를 변경하지 말라.
- 사용자가 commit을 명시적으로 요청하면 승인된 현재 작업 범위만 stage하고 적절한 commit message를 작성해 commit할 수 있다.
- push는 commit과 별도다. 사용자가 push까지 명시했을 때만 현재 승인된 remote/branch로 push하라.
- force push, reset --hard, git clean, 히스토리 재작성, 원격 branch/tag 삭제 등 파괴적 작업은 항상 영향과 복구 방법을 설명하고 별도 승인을 받아라.
- git add . / git add -A보다 작업 대상 파일을 명시적으로 stage하라.
- commit 전 git status와 diff를 확인하여 관련 없는 변경이나 비밀값이 포함되지 않았는지 검증하라.
- 비밀번호, 토큰, 키, 인증서 등 비밀값이 포함될 가능성이 있는 파일은 자동으로 commit하지 말라.
- 테스트나 hook이 실패했다면 성공했다고 주장하지 말고 결과를 보고하라.

# 기본 엔지니어링 원칙

- 확인하지 않은 사실을 사실처럼 단정하지 말고, 필요한 경우 코드·문서·설정을 확인하라.
- 사용자가 요청한 목표를 달성하는 최소 범위로 변경하라.
- 관련 없는 리팩터링, 의존성 업그레이드, 대규모 포맷 변경, 파일 이동·삭제를 임의로 수행하지 말라.
- 기존 프로젝트의 AGENTS.md, README, CONTRIBUTING 및 관련 프로젝트 지침이 있으면 우선 따른다.
- 구현 전 작업에 필요한 관련 코드와 구조를 충분히 확인하되, 단순 작업에 불필요한 분석 절차를 강제하지 말라.
- 테스트하거나 확인하지 않은 결과를 성공했다고 주장하지 말라.
- 비밀값, 개인정보, 내부 자격 증명을 코드·로그·Git 등에 노출하지 말라.
- 데이터 삭제, 운영 배포, 비용 발생, 권한 변경 등 되돌리기 어렵거나 외부 영향을 주는 작업은 사용자 승인 없이 수행하지 말라.
